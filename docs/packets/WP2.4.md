## Goal

The four CI adapters are hand-written prose that restates the pipeline's stage wiring; they have
already drifted (Jenkins is missing entirely) and nothing stops the next drift. Make them
**generated output**: one template in core renders all four (GitHub Actions, GitLab CI, Azure
Pipelines, Jenkins) from `pipeline.STAGES` + one stage-to-trigger binding table, `make ci-adapters`
regenerates the committed files with **zero diff**, and a drift test + parity test keep the YAML
from diverging from the code — exactly how `make schema` and `make capabilities` already work.
**No logic in the rendered files**: they only bind platform events to `evalops pipeline <stage>`
and plumb the documented env vars; all stage behaviour stays in `src/evalops/pipeline.py`.

The design decisions below are **fixed**. Do not re-derive or widen them; if one is impossible,
stop and report a blocker with the failing evidence.

### A. The template (`src/evalops/ci_adapters.py`, new core module)

- **A1** `ADAPTERS: dict[str, AdapterSpec]` with exactly four entries, keys `github, gitlab, azure,
  jenkins`. `AdapterSpec` is a frozen dataclass: `name`, `path` (the committed file, relative to the
  repo root: `ci/github-actions.yml`, `ci/gitlab-ci.yml`, `ci/azure-pipelines.yml`, `ci/Jenkinsfile`),
  `description`, `render` (the function producing the file's bytes). Stage names come from
  `pipeline.STAGES` (import it — never restate the four names as literals in the spec table).
- **A2** One shared binding table maps each stage to per-platform trigger plumbing (data, not
  strings-in-a-heredoc): stage → the platform condition that runs it and the env vars it needs.
  The current hand-written files are the semantic reference for the bindings (keep their
  behaviour: pr on pull_request/merge_request/PR builds with `EVALOPS_PR` + `EVALOPS_BRANCH`;
  main on push to the default branch with `EVALOPS_BRANCH` = default; nightly on schedule;
  release manual with an `EVIDENCE_GROUP` input/parameter). Python 3.11, `pip install -e
  ".[${PIP_EXTRAS}]" -r requirements.txt` and `fetch-depth: 0`/full-clone checkout stay, as data
  constants of the template.
- **A3** Every rendered adapter invokes the stages **only** through the shim:
  `bash ci/pipeline.sh <stage>` (Jenkins: `sh 'bash ci/pipeline.sh <stage>'`). No rendered file may
  invoke any other evalops subcommand (`sync`/`eval`/`gate`/`promote`/`baseline`/`calibrate`/
  `plan`/`doctor`/`guard`), define fallbacks/defaults for stage behaviour, or branch on stage
  outcomes. Platform-native conditionals (`if:`/`rules:`/`condition:`/`when:`) that **select when a
  stage runs** are bindings, and are allowed; anything that changes *what a stage does* is logic,
  and is forbidden. Fork-PR handling is **not** rendered as conditionals: `EVALOPS_PR` already
  routes state commits to the bot branch (WP2.2); the pr job sets `EVALOPS_PR` from the platform's
  PR number and a short comment explains the fork/bot-branch story — no `head.repo`-style gating in
  the output.
- **A4** Each rendered file starts with a header comment naming the generator:
  `generated by 'make ci-adapters' from src/evalops/ci_adapters.py — edit the template, not this
  file` (platform comment syntax per file: `#`, `#`, `#`, `//` for the Jenkinsfile).
- **A5** Rendering is deterministic and offline: the same template version renders byte-identical
  output (no timestamps, no hostnames, sorted where the format allows). The three YAML files must
  parse with `yaml.safe_load` after rendering; the Jenkinsfile must be a declarative pipeline whose
  `stages` cover exactly the four stage names, in `pipeline.STAGES` order (structural assertions —
  no Jenkins runtime offline).

### B. `evalops ci-adapters [--write] [--dir <path>]` (cli.py: one subcommand)

- **B1** Default (no `--write`): report only — `data.adapters` = one entry per adapter
  (`{name, path, stages, bytes}`, deterministic, sorted by name), exit 0, nothing written.
- **B2** `--write` renders all four and writes them under `--dir` (default: the repo root, so
  `ci/...` paths land in `ci/`). `data.files_written` lists the written paths (sorted). It
  overwrites without asking (a generator, like `write_schema`); it never writes anything else
  (exactly four files, even on re-run). `--json` envelope rules as every command.
- **B3** Missing/wrong `--dir` (not a directory) is exit 2. Unknown adapter names are impossible by
  construction (the dict is the spec table) — no flag selects a subset in this WP.

### C. `make ci-adapters` (Makefile: one additive target, beside `schema`/`capabilities`)

- **C1** `ci-adapters:` target: `PYTHONPATH=src $(PYTHON) -c "from evalops.ci_adapters import
  write_adapters; print(write_adapters())"` — same shape as the two existing generators.
  `write_adapters(root: Path) -> list[str]` renders + writes all four and returns the written paths.
- **C2** Add the target to the `.PHONY` list on the same line pattern.

### D. Tests (`tests/unit/test_ci_adapters.py`, new)

- **D1** **Zero-diff drift test** (the schema/capabilities pattern): run `write_adapters` against
  the repo's real `ci/` directory and assert every rendered file is byte-identical to the committed
  one; a mismatch names the file. This is what makes hand-edits impossible to merge.
- **D2** **Parity test:** for each adapter, every stage name in `pipeline.STAGES` appears exactly
  once as `ci/pipeline.sh <stage>`; no other evalops subcommand appears anywhere in the rendered
  text; adding a stage to `STAGES` on a /tmp copy of the module (or monkeypatching) makes the
  parity assertion red — the adapters cannot silently forget a stage.
- **D3** **No-logic-in-output test:** the rendered YAML files contain no `evalops <subcommand>`
  invocations beyond the shim line, and their only shell lines are checkout/install/shim (assert
  structurally: parse the YAML, walk the steps/scripts, match against the allowlist of command
  prefixes: `git`, `pip`, `bash ci/pipeline.sh`, platform helper tasks).
- **D4** **Determinism + validity:** render twice → byte-identical; `yaml.safe_load` parses both
  YAML files; the Jenkinsfile structurally matches the §A5 assertions; every rendered file starts
  with the §A4 header.
- **D5** **CLI paths:** `evalops ci-adapters --json` reports four sorted adapters and writes
  nothing (a `--write` into a temp dir writes exactly four files at the spec'd relative paths and
  lists them in `data.files_written`; a second identical run is byte-identical; `--dir` pointing at
  a file is exit 2). Mutation-sensitivity for D1/D2 proven on a /tmp copy (one mutation each: edit
  a committed file → D1 red; add a stage → D2 red).

## Falsifiable done-when

- **H1** `make ci-adapters` on a clean tree exits 0 and produces **zero diff** (the committed files
  are the generated ones); a second run is byte-identical.
- **H2** `evalops ci-adapters --json`: one envelope, `command: "ci-adapters"`, exit 0,
  `data.adapters` sorted, nothing written; `--write` into a temp `--dir` writes exactly
  `ci/github-actions.yml`, `ci/gitlab-ci.yml`, `ci/azure-pipelines.yml`, `ci/Jenkinsfile` under it.
- **H3** The rendered GitHub workflow binds all four stages to the same events as the current
  hand-written file (pull_request / push-main / schedule / workflow_dispatch with the
  `EVIDENCE_GROUP` input), sets `EVALOPS_PR` + `EVALOPS_BRANCH` on the pr job, and no rendered file
  contains stage logic or non-shim evalops invocations (D3 red if violated).
- **H4** Jenkins exists for the first time: a declarative `ci/Jenkinsfile` covering exactly the
  four stages in `pipeline.STAGES` order, each stage a single `bash ci/pipeline.sh <stage>` call.
- **H5** Drift + parity are enforced: D1 red after editing a committed adapter (mutation evidence
  in the report), D2 red after adding a stage to `STAGES` (on a copy).
- **H6** `make check` green (329 → new total), standalone runner green, `make contract` skips,
  `make schema` zero drift, `make capabilities` zero diff, and `git status --short` lists only:
  `src/evalops/ci_adapters.py` (new), `src/evalops/cli.py` (one subcommand), `Makefile` (one target
